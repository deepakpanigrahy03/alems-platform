# Sandbox Layout and Path Resolution

---
**Status:** PRODUCTION
**Applies to:** `alems sandbox create|init|info|doctor`, every run
**Last updated:** 2026-10-06
---

## Overview

A-LEMS separates three things:

| Concept | What it holds | Lives in git |
|---|---|---|
| Engine | the platform code and its virtual environment | engine repository |
| Sandbox | one study: profiles, configuration overrides, datasets, lock file | sandbox repository |
| Data root | stores, logs, error records, machine configuration | never |

A sandbox never contains data, host paths, endpoints, or credentials. Host specific values live in the uncommitted file `.sandbox-env` and in `~/.alemsrc`.

## Store Layout

Every sandbox store lives under its owner, so users never share a store even with identical sandbox names:

```
<data_root>/<host>/users/<user>/sandboxes/<name>/experiments.db
<data_root>/<host>/users/<user>/sandboxes/<name>/logs/       store log and per run logs
<data_root>/<host>/users/<user>/sandboxes/<name>/errors/     error records
<data_root>/<host>/users/<user>/active-sandbox               the sandbox selected by alems sandbox use
```

`<user>` is the login name (`$USER`); `<host>` is the lower case host name. Logs and errors always sit beside their store.

Sandboxes created before this layout keep their store at `<data_root>/<host>/sandboxes/<name>/` and continue to work unchanged. The engine directory itself uses the environment layout `<data_root>/<host>/envs/<user>/<env>/<project>/experiments.db`, again with its logs and errors beside the store.

## How a Command Finds Its Store

Highest priority first; the first match wins:

1. `--store <path>` or `--sandbox <path>` on the command line
2. `ALEMS_STORE` in the environment (shell, or `.sandbox-env`)
3. `ALEMS_SANDBOX` in the environment
4. the nearest `alems-sandbox.yaml` above the current directory
5. the active sandbox (`users/<user>/active-sandbox`)
6. the environment layout of the engine (`envs/<user>/<env>/<project>`)
7. an error that names every place checked

`alems sandbox info` shows the store a command will use; `alems sandbox doctor` checks that the recorded locations agree.

## The Sandbox Machine File `.sandbox-env`

`alems sandbox create` and `alems sandbox init` generate it. It is plain `NAME=value`, so a shell can `source` it, and A-LEMS reads the same file at startup. It is parsed, never executed: only lines of the form `UPPER_NAME=value` are taken, and `${VAR}` references expand. A variable already set in the shell wins over the file.

Optional lines are generated commented out with the values in effect, so uncommenting a line pins exactly what is used now. A generated file looks like this:

```bash
# .sandbox-env -- machine-generated, do not commit
# Generated by: alems sandbox create / alems sandbox init
# Sandbox: sand_log
# Regenerate on a new machine: alems sandbox init
#
# ── Auto-generated (do not edit) ──────────────────────────────
ALEMS_STORE=${ALEMS_DATA_ROOT}/gn100-2b96/users/dpani/sandboxes/sand-log/experiments.db
ALEMS_SANDBOX=/home/dpani/sandboxes/sand_log
#
# ── Data and record locations: values in effect now (uncomment to pin) ──
# Precedence: shell environment, then this file, then these defaults.
# ALEMS_DATA_ROOT=/mnt/alems-data
# ALEMS_LOG_DIR=${ALEMS_DATA_ROOT}/gn100-2b96/users/dpani/sandboxes/sand-log/logs
# ALEMS_ERROR_DIR=${ALEMS_DATA_ROOT}/gn100-2b96/users/dpani/sandboxes/sand-log/errors
# ALEMS_HEARTBEAT_S=1
#
# ── Per-sandbox endpoint overrides (edit these) ────────────────
# ALEMS_VLLM_API_URL=http://your-server:8000/v1
# ALEMS_SGLANG_API_URL=http://your-server:30000/v1
# ALEMS_OLLAMA_API_URL=http://localhost:11434
# OPENAI_API_KEY=sk-...
# ANTHROPIC_API_KEY=sk-ant-...
```

Example: send the logs of one study to a fast local disk. Uncomment and edit one line, nothing else:

```bash
ALEMS_LOG_DIR=/fast-disk/ispass/logs
```

## The Sandbox Manifest `alems-sandbox.yaml`

The manifest identifies the study and is committed with it. It validates against the published schema `schemas/sandbox-manifest.schema.json`; unknown keys are rejected.

```yaml
author: dpani
created_at: '2026-10-06'
description: 'ISPASS 2027 energy attribution experiments'
engine: /home/dpani/mydrive/alems-platform
engine_version: 1.0.0
extensions: []
name: sand-log
sandbox_format_version: 1
sandbox_id: 026abca1-1092-4728-873b-796f4ea69fd0
sdk_version: '>=1.0.0,<2.0.0'
store: /mnt/alems-data/gn100-2b96/users/dpani/sandboxes/sand-log/experiments.db
```

`sandbox_id` is generated once at creation and never changes; it is also recorded inside the store (`sandbox_identity`).

## Configuration Precedence

Lowest to highest: engine templates, plugin defaults, machine configuration (`<data_root>/<host>/config/`, `~/.alemsrc`), the sandbox `config/` overrides and `.sandbox-env`, the profile, the command line.


## Verification

```bash
alems sandbox create ~/sandboxes/layout_check
cd ~/sandboxes/layout_check
alems sandbox info | grep store
grep '^ALEMS_STORE' .sandbox-env
python3 -c "from core.storage.resolver import resolve_store; from core.observability import locations as l; print(resolve_store()); print(l.host_log_dir()); print(l.error_dir())"
```

Every printed path contains `users/<your login>/sandboxes/layout-check/`. Remove the check sandbox afterwards (its directory and its store directory).

## Known Limitations

- **Location recorded in more than one place:** the manifest `store` key and `ALEMS_STORE` in `.sandbox-env` both record the store. Moving a store by hand requires updating both, then running `alems sandbox doctor`.
- **Older sandboxes:** stores created before the per user layout stay at `<data_root>/<host>/sandboxes/<name>/` until moved.
- **Manifest host paths:** `engine` and `store` in the manifest are host paths; on another machine run `alems sandbox init` and correct them before the first run.
